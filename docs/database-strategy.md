## Identity Handling Strategy

### Classification

| Strategy | Count | Tables |
|----------|-------|--------|
| GENERATED BY DEFAULT | 16 | adapterconfig, directorylocation, emailaddress, emailgroup, emailgroup_emailaddress, facsmessageentity, facsmessagehistoryitementity, gicsawasyncmessage, jmssystemadaptermessage, jmssystemadaptermessagestatus, recipient, recipient_dirlocations, recipient_emailgroup, recipient_webservices, smsmessagelog, webservicestatusmessage |
| GENERATED ALWAYS | 4 | incomingfile, outboundemail, remote_interaction_log, voc_message_log |
| No identity | 1 | webservice |
| Composite PK (no identity) | 5 | role_accessright, userrole, wealthaccessright, recipient_webservices, recipient_emailgroup |

### GENERATED BY DEFAULT Handling

Standard INSERT with explicit ID values. No special handling needed. DB2 accepts explicit values for BY DEFAULT columns.

After all rows are inserted, reset the DB2 identity sequence:

```sql
ALTER TABLE WEALTHADAPTER.<table> ALTER COLUMN <id_col>
  RESTART WITH <max_id + 1>;
```

### GENERATED ALWAYS Handling

DB2 rejects explicit ID values for GENERATED ALWAYS columns in standard INSERT. Two options:

**Option A — ALTER to BY DEFAULT (preferred for small tables)**

```sql
-- Before import
ALTER TABLE WEALTHADAPTER.<table> ALTER COLUMN <id_col>
  SET GENERATED BY DEFAULT;

-- INSERT with explicit IDs ...

-- After import
ALTER TABLE WEALTHADAPTER.<table> ALTER COLUMN <id_col>
  SET GENERATED ALWAYS;
ALTER TABLE WEALTHADAPTER.<table> ALTER COLUMN <id_col>
  RESTART WITH <max_id + 1>;
```

**Option B — LOAD with IDENTITYOVERRIDE (required for large tables)**

```sql
-- Export to CSV, then:
LOAD FROM <file> OF DEL
  MODIFIED BY IDENTITYOVERRIDE
  INSERT INTO WEALTHADAPTER.<table>;
```

Option B is necessary for `incomingfile` (~8.5K rows), `outboundemail` (~222K rows), and potentially `remote_interaction_log` (164 rows) if ALTER is not permitted on production-like environments.

### No Identity — webservice

The `webservice` table has no identity column. IDs are application-managed. INSERT statements must include the ID value explicitly. No sequence reset needed.

### remote_interaction_log Sequence Gap

The PG sequence `remote_interaction_log_id_seq` is at ~45.6M despite only 164 rows existing. A scheduled batch job periodically bulk-deletes old rows. After rollback, DB2's sequence should be set to MAX(id) + 1 from the actual data, not from PG's sequence value.

## Trigger Handling

### userdetail Triggers (DB2)

DB2 has three active triggers on `WEALTHADAPTER.USERDETAIL`:

| Trigger | Event | Action |
|---------|-------|--------|
| NEW_USERDETAIL | AFTER INSERT | INSERT into WEALTH.CHGDATALOG |
| UPDATE_USERDETAIL | AFTER UPDATE | INSERT into WEALTH.CHGDATALOG |
| DELETE_USERDETAIL | AFTER DELETE | INSERT into WEALTH.CHGDATALOG |

**Decision: Leave triggers ACTIVE during rollback.**

Rationale:
- WEALTH.CHGDATALOG exists in the same DB2 instance and is accessible from the WEALTHADAPTER schema context
- The triggers record change history, which is desirable — the rollback data import is a legitimate change
- Only 861 rows in userdetail, so trigger overhead is negligible
- Disabling triggers on DB2 requires `ALTER TABLE ... ALTER FOREIGN KEY ... NOT ENFORCED` patterns and risks leaving the table in an inconsistent state if the rollback crashes

### userdetail Triggers (PostgreSQL — informational)

PG has equivalent triggers but they are non-functional because `wealth.chgdatalog` does not exist in the adapter PG database. If data ever needs to flow from DB2 back to PG, disable triggers first:

```sql
ALTER TABLE wealthadapter.userdetail DISABLE TRIGGER ALL;
-- Import data
ALTER TABLE wealthadapter.userdetail ENABLE TRIGGER ALL;
```

## Large Table Strategy

### jmssystemadaptermessagestatus (~39.1M rows)

This is the largest table and the primary performance bottleneck.

**Approach: Streaming batch INSERT with parallel workers**

1. **Batch size**: 5,000 rows per INSERT statement
2. **Commit interval**: Every 5,000 rows (1 batch = 1 commit)
3. **Workers**: 4 parallel connections, each processing a PK range
4. **PK partitioning**: Divide the PK range into 4 segments, one per worker
5. **Checkpoint**: After every batch, per worker
6. **Estimated time**: ~72M rows ÷ 5,000 per batch = 14,400 batches. At ~50ms per batch with 4 workers: ~3 minutes. Network latency will dominate — estimate 30-60 minutes total.

**Fallback: DB2 LOAD utility**

If INSERT performance is unacceptable (>2 hours), export to CSV and use DB2 LOAD:

```sql
LOAD FROM jmssystemadaptermessagestatus.csv OF DEL
  METHOD P (1, 2, 3, ..., N)
  INSERT INTO WEALTHADAPTER.JMSSYSTEMADAPTERMESSAGESTATUS;
```

LOAD bypasses logging and constraint checking, achieving 10-100x throughput improvement.

### facsmessagehistoryitementity (~12.7M rows)

Second largest. Same streaming batch strategy as above. FK dependency on `facsmessageentity` — must complete facsmessageentity first.

### gicsawasyncmessage (~9.8M rows)

No FK dependencies. Can run in parallel with other large tables.

## Checksum Algorithm

For post-migration validation, the toolkit computes a deterministic checksum per table:

1. SELECT all columns (excluding source-only columns) ORDER BY primary key
2. For each row, concatenate all column values as UTF-8 strings with `|` delimiter
3. NULL values are represented as the literal string `\N`
4. TIMESTAMP values are formatted as ISO 8601 with microsecond precision: `2026-08-24T14:30:22.123456`
5. CLOB/TEXT values are included as-is (not truncated)
6. BLOB/BYTEA values are hex-encoded
7. Compute SHA-256 over the concatenated row strings (newline-separated)
8. Compare source and target SHA-256 digests

For tables with more than 1M rows, use a sampling strategy: checksum every Nth row where N = total_rows / 100,000.

## Encoding and Codepage Considerations

| Aspect | PostgreSQL | DB2 | Risk |
|--------|-----------|-----|------|
| Database encoding | UTF-8 | UTF-8 (UNICODE codepage) | Low — same encoding |
| VARCHAR semantics | Character length | Byte length (default) | Medium — multi-byte characters may exceed DB2 byte limit |
| CLOB handling | TEXT (unlimited) | CLOB (2GB max) | Low — no adapter CLOBs approach 2GB |
| XML storage | TEXT column | XML column type (if applicable) | Medium — outboundemail.xmlcontent |
| NULL handling | Standard SQL NULL | Standard SQL NULL | None |
| Timestamp precision | Microsecond (6 digits) | Microsecond (6 digits, DB2 10.5+) | Low — verify DB2 version supports 6-digit fractional |

### XML Column Handling

The `outboundemail.xmlcontent` column stores XML content as TEXT in PG. If DB2 stores it as XML type, the INSERT must cast:

```sql
INSERT INTO WEALTHADAPTER.OUTBOUNDEMAIL (..., XMLCONTENT, ...)
VALUES (..., XMLPARSE(DOCUMENT ? PRESERVE WHITESPACE), ...);
```

If DB2 stores it as CLOB or VARCHAR, no casting is needed — verify column type during schema comparison.
